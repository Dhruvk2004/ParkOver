ParkOver Launch Audit

Every driver journey checked against the code and against parking apps that are live today (Park+, SpotHero, JustPark, PayByPhone, Get My Parking, BMC's own plans). What is real, what is mocked, what is missing, and what to build before the Play Store.

The short version

ParkOver is a well-built booking front end over parkings that don't know it exists. Search, live free-now counts, double-booking protection and the booking flow are real and tested. But the 104 parkings come from a static JSON file, no operator sees a booking, nobody checks a car in, and no money moves. A driver who books today arrives at a gate that has never heard of the reservation.

The missing half is the operator side: lots, prices, capacity and payouts managed by the people who run the parking, with payments chained to them. That, plus payments, legal pages and account deletion, is what stands between this build and a public launch.

Part 2

The missing half: operators and admin

Every serious parking app has an operator side. SpotHero has a Control Panel for rates, inventory and revenue [9]. JustPark owners list a space in about ten minutes [10]. Get My Parking is an operator platform with an admin dashboard, plate cameras and gate kits [1]. ParkOver has none, so a booking reaches nobody.

Admin (you)

Run the marketplace

  • Approve operators after KYC (PAN, bank, GST if any)
  • Create or approve lots; set the platform commission
  • See all bookings, refunds, disputes and support tickets
  • Payout reports and reconciliation
Operator dashboard (web)

Manage their lots

  • Lot details: address, pin, photos, hours, closed days
  • Capacity per vehicle type and floor; real bays if they sell them
  • Prices: hourly, daily, monthly passes; holiday overrides
  • Today's bookings, occupancy, revenue, payouts
  • Turn a lot off ("full", "closed for an event")
Attendant app (phone)

Work the gate

  • Scan the driver's QR → verify → mark arrived
  • Scan or tap at exit → mark completed, show overstay due
  • Record drive-in cars so free-now is true
  • Works offline at basements; syncs later

How payments chain to operators

  1. Driver confirms → ParkOver's server creates a gateway order for the lot's price (never trust the price from the phone).
  2. Driver pays by UPI intent, card or wallet → the gateway's webhook hits the server → the booking becomes CONFIRMED and PAID. Slots are held for 10 minutes while unpaid.
  3. The payment is tagged with the lot's operator. With Razorpay Route, the operator's share goes to their linked account and ParkOver keeps its commission automatically [26].
  4. Cancellation inside the policy → automatic refund through the gateway; no-show → per policy.
  5. Attendant scans at entry and exit; overstay is charged at exit.
  6. Weekly payout report per operator; GST invoice per booking.

What it changes in the data

  • operators/{id}: KYC status, bank/linked account, commission
  • parkings/{id} in Firestore, owned by an operator. This replaces the GitHub JSON, so the rules can finally check capacity.
  • payments/{id}, refunds/{id}, written only by the server
  • Roles in auth claims: driver, attendant, operator, admin

What it needs that the app can't do

  • A server. Orders, webhooks, refunds, payouts, reminders and expiring no-shows can't run on the phone.
  • Firebase Cloud Functions need the paid Blaze plan; a free alternative is a Cloudflare Worker (also the planned routing proxy).
  • The operator dashboard is a web app; it can share code with an iPhone web version (Part 4).

  • KYC to open the account: a sole proprietor needs PAN, address proof and 2 of Udyam/GST/Shop Act/IEC/bill; a Pvt Ltd needs incorporation documents and director KYC [27]. Gateways also check that the website, terms, refund and privacy pages are live (practice; not sourced).

Part 4

Reaching iPhone drivers

Android dominates phones in India, but car owners skew higher-income, where iPhones are common. Park+ alone has an iOS app rated 4.7 from about 168K ratings [6]. Losing those drivers matters most in exactly the places ParkOver targets (BKC, Lower Parel, malls, the airport).

Part 5

What I'd do, in order

Before any public release

  • Privacy policy, terms, cancellation and refund policy; link them in the app.
  • In-app account deletion plus a web deletion link (Play policy).
  • Honest copy: "bays you can book", not "real-time availability"; hide made-up ratings; drop invented EV and accessible bays.
  • Enforce opening hours in booking; fix the GST rate on the price breakdown.
  • Support that reaches a person (email or WhatsApp at minimum).
  • App Check, Storage rules, routing proxy, restrict the flagged Firebase key.
  • Play Console checklist: Data safety form, content rating, target API, and, for a new personal developer account, the closed test with testers before production access (check the exact rule in your Play Console).

Pilot (5–10 partner lots)

  • Move parkings to Firestore with capacity; a minimal admin page to edit them.
  • Attendant scanner app: entry and exit set ACTIVE and COMPLETED; auto-expire no-shows.
  • Pay at parking, but with operator agreements in place, so a reservation is real.
  • Local booking reminders; a "drive-in" button for attendants so free-now is true.

Before scaling

  • Business entity, gateway KYC, CA sign-off on GST/TCS; a small server for orders, webhooks, refunds and reminders.
  • In-app UPI and cards; split payouts (Route or Cashfree Easy Split); invoices.
  • Operator web dashboard (lots, prices, passes, payouts); mobile web booking for iPhone users.
  • Reviews from completed stays; phone OTP login.

Later

  • Monthly passes, corporate parking, FASTag through an acquirer bank, plate recognition.
  • Native iOS with Compose Multiplatform.
